# Audio, call and TTS — rc.37 source-confirmed contract

Audio is a separate session from MSE/RTC video. The server checks current HA user grants (`overview:manage` or `stations:manage`, plus station scope), connection-bound PanelSecurity and station runtime. Three audio+TTS sessions total, at most one per station and at most one per HA connection. `audio_busy` is returned on conflict. A future delegated transport must define what its connection identity means before audio can be delegated; it cannot pass a token through another connection.

## Audio subscription and packets

`hikvision_intercom/audio/start` request: exactly `{id,type,station_id}` where station_id is a string up to 128 chars. Success is an empty HA result for that ID, then an event on that ID with `{format:"hikvision_intercom.audio",state:"ready",token:<32 hex chars>,sample_rate:8000,packet_bytes:800,max_seconds:180}`. The token is tied to the same HA connection and is not a reusable URL. A session has a 180-second maximum and closes after 12 seconds without activity. A `closed` event has `reason` and `close_confirmed:boolean|null`; no further audio event on that subscription is expected after cleanup. Errors include unauthorized, invalid_fields, station_unloaded, audio_busy and later connection/device codes.

`audio/send`: `{id,type,token,sequence,data}` exactly. `sequence` is a strict integer starting at 0; `data` is base64 of **800 G.711 µ-law bytes** (1068 base64 characters). Result `{sequence:<next integer>}`. `audio/receive`: `{id,type,token}` exactly; result `{format:"hikvision_intercom.audio",data:<base64 packet>}`. Only one receive may be outstanding per session (`audio_backpressure`). `audio/mute` and `audio/diagnostics` take `{id,type,token}`; mute returns `{}`, diagnostics returns accepted packet/byte, received/signal byte, dropped packet, upload HTTP status and `physical_result:"unverified"` counters. `audio/send` failures such as sequence mismatch or malformed base64 use `audio_invalid_packet`. `audio_not_started` means the token/connection/session is no longer valid.

The internal station path uses 8 kHz G.711 µ-law. A 160-byte frame is 20 ms; the exposed 800-byte packet is 100 ms. Client pacing is roughly 10 packets/s while transmitting, subject to device and browser timing. The server accepts the source audio channel only when it advertises the observed 8 kHz G.711 µ-law capability; it does not rewrite the station codec. Microphone playback uses the existing AudioWorklet resampling path in WisKey frontend; Arx must build/test its own microphone and output routing if it does not reuse that code. `talk_mode` is UI behavior (PTT/toggle), not a change in this packet contract. Full-duplex audible behavior has not been proved for all devices. Browser microphone requires permission and explicit user gesture, and must stop on navigation/background/revocation.

**Correction to Arx request:** rc.37 registers `audio/start`, `audio/send`, `audio/receive`, `audio/mute` and `audio/diagnostics`; it does **not** register a `hikvision_intercom/audio/stop` WebSocket command. Closing/unsubscribing the `audio/start` HA subscription invokes the server cancel callback; closing the socket also releases it. The frontend uses subscription cleanup. Do not implement `audio/stop` unless a future version advertises it.

## TTS

`tts/engines` returns `{default:string|null,engines:[{engine_id,name,supported_languages:string[],default_language:string|null}]}` after the same manage grant. `tts/start` takes exactly `{id,type,station_id,engine_id,language,message}`; `language` may be null, message is normalized whitespace with 1–500 characters, station/engine IDs 1–128 characters. Success creates a subscription under that ID. Events carry `format:"hikvision_intercom.tts"`: `generating`; `speaking` with `duration_seconds` and `packet_count`; `completed` with `duration_seconds`, `bytes_written`, `physical_result:"unverified"`; or `closed` with `reason` on a non-completed path. TTS synthesis has a 30-second timeout and shares the audio station/global/connection capacity. A completed software state or accepted packet is not proof a person heard speech at the station.

## Call signalling and field proof

`media/call` reads the station call context; `media/signal` accepts answer/reject/hangUp through WisKey's station call handler. Call signalling state and actual audible talkback are separate. Two simultaneous operators require a site concurrency test; do not promise that both can answer or that the second always receives a particular code without testing the station/model path. For field acceptance record: station model/firmware, timestamp, HA/Arx versions, browser/device, call state before/after, microphone packet counters, receive bytes, human confirmation at station and any device-side evidence. Software counters alone are insufficient.
