# Data dictionary for native Arx screens (rc.37)

This section documents the primary public projections needed for Gates B–C. It is not a declaration that every P2/P3 nested workflow object has a frozen schema; see `README.md` and the generated catalog. IDs are opaque: a person/card ID is a UUID string in current storage, while station ID is its HA config-entry ID. Do not reconstruct or parse an ID to infer authorization or device identity. Most stored times are ISO 8601 with timezone; person `valid_from`/`valid_until` are normalized to UTC seconds and must be ordered from 1970-01-01 through 2037-12-31. `overview.default_zone` is `{kind:"iana",name:<HA configured IANA zone>}` for display; it does not change UTC storage.

## Person

Public `ManagedUser.public()` returns: `id`, `employee_no`, `display_name`, `phone`, `access_category` (`staff|visitor|contractor`), `responsible_person`, `access_purpose`, `archived_at`, `access_timing_draft`, `access_timing_policy`, `active`, `user_type` (currently `normal`), `valid_from`, `valid_until`, `assignments`, `revision`, `created_at`, `updated_at`, `identity_locked`, `profile` (custom field ID → string), `group_ids`, `permission_overrides`, plus `photo_configured`, `pin_configured` and public `cards`. Plain PIN, full card number and photo body are **not** in the standard person response. Under operator restrictions see `SCOPES.md` for exact placeholders, `operator_editable` and `redacted_fields`. Phone is a normalized contact string, at most 32 characters, 7–15 digits, optionally starting `+`; do not use it as a unique identity key.

Person `revision` is for optimistic updates to that person. `users/create` takes `{data,sync_now?}` with `sync_now` default `true`; `users/update` takes `{user_id,revision,data,sync_now?}`. `data` accepts only the server's `USER_FIELDS`: `employee_no`, `display_name`, `phone`, `active`, `user_type`, `valid_from`, `valid_until`, `pin`, `cards`, `assignments`, `door_permissions`, `permission_overrides`, `access_policy_revision`, `profile`, `group_ids`, `photo`, `access_category`, `responsible_person`, `access_purpose`, `access_timing_draft`, `access_timing_policy`. Absence of a PIN/card value in an update preserves existing secret material; an empty/missing field is not generally a deletion instruction. For guest/contractor, finite validity and responsible person are required. `sync_now` queues normal reconciliation; it does not prove a station accepted the change. A dedicated full nested `data` schema requires command-level extraction/tests and is **not delivered as a stable JSON Schema in this revision**.

Public card: `{id,masked_number,label,card_type,enabled}`; current supported `card_type` is `normalCard`. `masked_number` is `•••• ` plus last four digits when available; full card number is never returned on ordinary reads. A generated PIN is returned once by `users/pin_generate` as `{pin:<string>}` and is **not saved by that read/generation call**; Arx must protect it and explicitly submit it in a later authorized create/update. `pin_configured` only states presence, not value.

Assignment map is station ID → `{config_entry_id,enabled,allowed_locks:number[],schedule_template:string|null,desired_revision:number,applied_revision:number|null,sync_state,last_sync_at:string|null,last_error:string|null}` in the server's public user projection. `sync_state` enum is `synced|pending|syncing|offline|conflict|error|delete_pending`. `applied_revision` is evidence about reconciliation to a station, not proof of a physical door opening. For the UI, `synced` with applied revision matching desired is stronger than `pending`, but site validation remains distinct.

`users/query` requires `query:string` (max 160), `filters:object`, `offset:integer 0..10000000`, `limit:integer 1..200`, `snapshot:string` (max 64). Filters are `group`, `profile` (up to 32 field/value pairs), `station`, `rights` (`""|assigned|unassigned|disabled`), `state` (`""|active|inactive|expired|upcoming|archived`), `credential` (`""|pin|no_pin|card|no_card`), `sort` (`name|name_desc|employee`). Response has `records`, `total`, `total_all`, `profile_facets`, effective `offset`, `limit`, `next_offset`, `previous_offset`, current `snapshot` and `stale`. Snapshot hashes public user IDs/revisions and permission context; if `stale=true`, restart paging at zero rather than concatenate inconsistent pages. Search by card only matches four visible trailing digits; hidden fields are removed before filtering.

## Station, relay and overview

`overview.stations[]` / `stations/get` rows include: `id`, `name`, `lock_enabled`, `loaded`, `online`, `call_state`, `sync_state`, `last_error`, `scanned_at`, `scanning`, `scan_error`, `reconciled_at`, counts, `last_seen`, `last_poll_ms`, `last_access`, `model`, `firmware`, `host`, `entities`, `capabilities`, `observations`, `clock`, `event_status`, `integrated_locks`. `call_state` can be `idle|ringing|in_call|ending|unknown|unavailable`; additional data may be unavailable when offline. `integrated_locks[]` is `{physical_index,api_id,name?}` derived from managed relays in station config; Relay 2 is shown only when managed. `stations/test_unlock` requires station ID and `lock` physical index. Its successful WebSocket result is `null` after `runtime.async_unlock` returns; it does **not** carry a readback or prove movement. Offline/unloaded returns `station_offline`; known release errors include `release_in_progress`, `release_unconfirmed`, `connection_closed`, `lock_not_managed`, otherwise `action_failed`. Never auto-retry an uncertain release.

`overview` returns `version`, `api:{version,min_client,capabilities,commands}`, `access`, stations, users, `users_complete`, `user_count`, settings, `default_zone` and global synchronization/removal arrays. `overview/summary` builds the same permission-filtered station/settings view with `include_users=false`, so `users=[]`, `users_complete=false`, and `user_count` is computed for visible people without serializing them. Use summary for frequent station/dashboard refresh; use `users/query` for people. No measured latency/byte figures at 12 stations/2000 people are available from this workspace; benchmark on Arx's installation.

## Events and time

An access-event row contains `id` (HMAC-derived opaque ID), `station_id`, `timestamp`, `received_at`, `time_source:"device"|"received"`, `employee_no`, `person_name`, `door`, `api_door`, `authentication:"card"|"pin"|"unknown"`, `result:"granted"|"denied"|"unknown"`, `event_type`, `major`, `minor`, masked `card`, `recovered:boolean`, `source:"query"|"stream"`; event detail may add a portrait under separate field policy. A received-time fallback or recovered event is not equivalent to a live ring. The access-event cache holds at most 5,000 rows / 30 days, with dedupe by event ID across restarts. There is **no universal durable sequence number or replay cursor across all WisKey event sources**. Arx must not infer continuity after a disconnect from a successful `subscribe` reconnect.

`events/list` uses `{filters:{station_id?,person?,result?,authentication?,event_type?,door?,start?,end?,limit?,before?}}`. `limit` defaults to 100 and is 1..200. `result`, `authentication` and `door` enums are above; event_type is one of the `KINDS` mapping's public names (`access_granted`, `access_denied`, `door_unlocked`, `door_locked`, `contact_open`, `contact_closed`, `unlock_exception`, `attempt_limit`, `unlock_record`, `door_not_opened`, `door_not_closed`, `unknown`). `start/end` are timezone-aware instants and must be ordered; `before` is a retained event ID. Results are sorted newest-first by `(timestamp,id)` and return `{records,next,retention_days,capacity}`. If `before` has expired or was pruned, the query fails; there is no replay beyond retention. Refetch the retained window after reconnect and label any possible earlier history gap.

## Remaining domain objects

Profile/group settings, station programs, hold-open schedules, public codes, visits, approvals, conflict workflows and fleet alerts have separate revisioned stores and state machines. Their current shape is in the shipped `docs/integrations/*.md` files where a focused contract exists. There is no one cross-domain revision. A global “complete schema” for every nested P2/P3 record is **still open**; do not implement those screens from `commands.static.json` alone. WisKey will deliver focused versioned contracts before calling them native parity.
