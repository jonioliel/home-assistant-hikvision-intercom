# How Arx stays compatible as WisKey grows

WisKey is under active development. rc.37 and `api_contract=1` are a starting point, not a final feature inventory. Arx should implement a small compatibility layer rather than bind each screen to a release number.

1. On every operator connection call `authorization/session`, `overview/summary` or `overview`, and subscribe. Compare `overview.api.version`/`min_client` with Arx's supported range; use `api.capabilities` and `api.commands` to enable each generic command. Separate media/subscription handlers need their own probe or a future explicit capabilities extension. Never display an action merely because Arx shipped its button.
2. Preserve unknown additive response fields and tolerate new enum values with a neutral “unknown” view. For write requests send only documented keys for the negotiated contract. A missing capability or grant means disable the action, not guess a fallback command.
3. Treat each new WisKey release as a contract-diff event. Run `python tools/generate_static_catalog.py <new-WisKey-checkout> <output>` and compare command additions/removals, required keys, permission classifications, READ status and error-code literals. Any removal or changed required field needs an explicit migration review. Static diff does not replace runtime validation of nested schemas/responses.
4. Pin any shared component bundle and adapter to an exact WisKey version range. Add lifecycle, event and mobile snapshots before replacing an Arx-native screen. Keep the original WisKey panel and its embed v1 route available during the migration as a fallback.
5. For each WisKey handoff provide: integration version and commit, `CHANGES_SINCE_*`, generated catalog diff, exact source of new schemas, test evidence, sample sanitized replies, station/firmware coverage and unknowns. Arx returns its bridge version and parity checklist. Do not make a silent data-store or contract v1 change.

Suggested CI gate in Arx: unit tests for the bridge's per-operator identity, command allowlist, page snapshot restart, denied role, reconnect, access revocation and unknown error response; contract-diff test against a pinned `commands.static.json`; browser tests at 390/768/1440/1920; a separate manual gate for live media and physical operations. The generated catalog intentionally marks nested contracts incomplete, so CI must never interpret a passing static diff as authorization for new writes.
