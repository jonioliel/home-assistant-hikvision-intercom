# תוכנית פיתוח: תמיכה מקומית מלאה ב‑Akuvox ב‑Wiskey

סטטוס: מסמך תכנון למימוש עתידי, לפני בחירת דגמי הפיילוט  
עיקרון מחייב: כל התקשורת עם הציוד תישאר ברשת המקומית. אין תלות ב‑Akuvox SmartPlus, ב‑Hik‑Connect או בשירות ענן אחר.

## 1. מטרת המסמך

מטרת השינוי היא להפוך את Wiskey ממימוש שמותאם ל‑Hikvision למערכת רב־יצרנית, ולהוסיף ספק Akuvox בלי לפגוע בהתקנות Hikvision קיימות.

התוצאה הרצויה היא:

- אותה חוויית ניהול למשתמש, בלי קשר ליצרן.
- גילוי יכולות בפועל לפי דגם וגרסת קושחה.
- הפעלת דלתות, וידאו, אירועים, משתמשים והרשאות בתקשורת מקומית בלבד.
- תמיכה בכרטיסים, PIN, לוחות זמנים ו‑QR לפי יכולות הציוד.
- שמירה על תאימות לאחור לישויות, לשירותים, לנתונים ולהגדרות של התקנות Hikvision קיימות.
- הצגה ברורה של יכולות חסרות במקום להציג פעולה שאינה נתמכת.

המסמך אינו מניח שכל דגם Akuvox תומך בכל תכונה. Akuvox משתמשת בסכמות API וביכולות שונות בין משפחות מוצרים וגרסאות קושחה, ולכן התמיכה תיקבע לפי פרופיל דגם ובדיקת יכולות חיה.

## 2. תחום התמיכה

### 2.1 יכולות ליבה

- זיהוי הדגם, כתובת MAC, גרסת קושחה ומצב המכשיר.
- בדיקת זמינות, זמני תגובה ושגיאות אימות.
- רשימת ממסרים, מצבם והפעלתם.
- קלטי דלת, חיישן דלת, לחצן יציאה, חבלה ופריצה, כאשר קיימים.
- תמונת מצלמה, RTSP ו‑ONVIF לפי יכולות הדגם.
- אירועי שיחה, פתיחת דלת, כרטיס, PIN, QR, פנים וקלטים.
- קריאת יומני דלת ושיחות.
- משתמשים, כרטיסים, PIN, שיוך לדלת ולוח זמנים.
- QR מקומי לאורחים ולעובדים, בדגמים תומכים.
- שיחה דו־כיוונית ו‑TTS דרך SIP מקומי, לאחר הסמכה פיזית של הדגם.
- דיאגנוסטיקה וייצוא מידע מסונן מסודות וממידע אישי.

### 2.2 יכולות מתקדמות

- פנים, אימות דו־שלבי ולוחיות רישוי בדגמים שתומכים בכך.
- מספר ממסרים משתנה, כולל ציוד עם יותר משתי דלתות.
- מעליות וקומות דרך KONE או ממשקי Akuvox רלוונטיים.
- First Credential, מצב נעילה, Hold Open וחגים, כאשר קיימת דרך כתיבה מתועדת ובטוחה.

### 2.3 מחוץ לתחום

- SmartPlus ושירותי ענן של Akuvox.
- Bluetooth, Mobile Key, Apple Wallet או תכונה אחרת שדורשת שירות ענן או רישוי ענן.
- פתיחת פורטים מהאינטרנט אל Wiskey או אל האינטרקום.
- הבטחת תמיכה בתכונה על סמך שם משפחת מוצר בלבד.

## 3. מצב QR בציוד Hikvision הקיים

הדגם הקיים DS‑KV6124‑E1 אינו מציג QR כאמצעי אימות בדף הנתונים הרשמי. מצבי האימות המוצהרים בו הם כרטיס, PIN, Hik‑Connect ותחנה פנימית. לכן אין לתכנן שימוש במצלמה המובנית שלו כסורק QR בלי הוכחה אחרת מקושחה ומ‑API של דגם מסוים.

ניתן להוסיף QR מקומי להתקנה קיימת באחת משתי דרכים:

1. **קורא QR חיצוני ברשת:** הקורא שולח ל‑Wiskey את תוכן הקוד. Wiskey מאמתת תוקף, דלת ומספר שימושים, ואז מפעילה את הממסר דרך מנגנון הפתיחה הקיים של Hikvision.
2. **מסוף גישה עם QR:** מוסיפים מסוף Hikvision או Akuvox שתומך רשמית ב‑QR ומחברים אותו לבקר או למנעול המתאים.

בחלופה הראשונה, פתיחת הדלת תלויה בזמינות Wiskey ובתקשורת אל האינטרקום. אם נדרשת פעולה בזמן נפילת השרת, יש להוסיף בקר מקומי שמסוגל לשמור הרשאות או רשימת קודים בעצמו.

## 4. עקרונות ארכיטקטורה

### 4.1 שכבת תחום אחידה

ה‑UI, בסיס הנתונים וכללי ההרשאות יעבדו מול מודל כללי של תחנה, דלת, ממסר, משתמש ואמצעי זיהוי. קוד יצרן יישאר בתוך מתאם ייעודי.

מבנה מוצע:

```text
Wiskey domain and UI
        |
        v
IntercomProvider contract
        |
        +-- HikvisionProvider
        |
        +-- AkuvoxProvider
                |
                +-- HTTP API client
                +-- Action URL receiver
                +-- RTSP / ONVIF adapter
                +-- local SIP media adapter
```

אין להוסיף בדיקות מסוג `if vendor == akuvox` בשכבת המוצר. הבדלים בין יצרנים צריכים להיפתר דרך חוזה הספק, פרופיל הדגם ורשימת היכולות.

### 4.2 תאימות לאחור

- הדומיין הטכני הקיים של האינטגרציה יישאר ללא שינוי כדי לא לשבור התקנות HACS, ישויות ושירותים.
- כל רשומה קיימת תקבל `provider = hikvision` במיגרציה.
- מזהי ישויות ושמות שירותים קיימים יישמרו.
- שמות תצוגה יכולים להיות כלליים ולהציג את היצרן והדגם כתכונות.
- שינוי סכמת אחסון יתבצע בגרסאות עם מיגרציה אטומית ויכולת חזרה לגרסה הקודמת.

## 5. חוזה ספק מוצע

הממשק המדויק יותאם לשפת הפרויקט, אך גבולות האחריות צריכים להיות דומים למבנה הבא:

```python
class IntercomProvider(Protocol):
    async def probe(self) -> DeviceProfile: ...
    async def health(self) -> HealthStatus: ...

    async def list_relays(self) -> list[Relay]: ...
    async def trigger_relay(self, relay_id: str, duration_ms: int | None) -> None: ...
    async def list_inputs(self) -> list[DoorInput]: ...

    async def get_camera_streams(self) -> list[CameraStream]: ...
    async def snapshot(self, camera_id: str) -> bytes: ...

    async def list_users(self, cursor: str | None) -> Page[AccessUser]: ...
    async def upsert_user(self, user: AccessUser) -> ProviderUserRef: ...
    async def delete_user(self, provider_user_id: str) -> None: ...
    async def read_back_user(self, provider_user_id: str) -> AccessUser: ...

    async def list_schedules(self) -> list[AccessSchedule]: ...
    async def upsert_schedule(self, schedule: AccessSchedule) -> ProviderScheduleRef: ...

    async def list_door_events(self, since: datetime) -> list[DoorEvent]: ...
    async def get_call_state(self) -> CallState: ...
    async def dial(self, target: str) -> None: ...
    async def hangup(self) -> None: ...
```

פעולה שאינה נתמכת תחזיר שגיאת `UnsupportedCapability` עקבית. אין לדמות הצלחה ואין להפעיל נתיב חלופי שלא הוגדר במפורש.

## 7. גילוי ויצירת פרופיל Akuvox

תהליך הוספת תחנה:

1. המשתמש מזין כתובת IP מקומית ופרטי גישה.
2. Wiskey בודקת HTTPS ולאחר מכן HTTP רק אם הוגדר במפורש והציוד אינו תומך HTTPS.
3. מתבצעת קריאת מידע מערכת, למשל דרך `/new_api/system/info` כאשר הנתיב קיים.
4. מזוהים דגם, MAC וגרסת קושחה.
5. נבדקים באופן לא הרסני נתיבי מצב, ממסרים, קלטים, משתמשים, יומנים ושיחה.
6. נבדקות כתובות RTSP ו‑ONVIF.
7. נבנה `DeviceProfile` ונשמר מטמון עם גרסת סכימה.
8. המנהל רואה מסך יכולות לפני שמירת התחנה.
9. בדיקת ממסר מתבצעת רק ביוזמת מנהל, עם בחירת דלת ואישור מתוך אשף ההגדרה הקיים.

פרופיל דגם מכיל התאמות סכימה בלבד. הוא אינו עוקף תשובה מפורשת מהמכשיר. יש לשמור fixtures מסוננים מכל דגם מוסמך כדי למנוע נסיגות.

## 9. HTTP API של Akuvox

לקוח ה‑API צריך לתמוך ב:

- Basic ו‑Digest לפי הגדרת המכשיר.
- Allowlist רק כהגנה נוספת, ולא כאימות היחיד כאשר אפשר להשתמש בסיסמה.
- HTTPS עם אימות תעודה או pinning בהתקנות מנוהלות.
- timeout קצר, retry מדוד לפעולות קריאה ו‑circuit breaker בעת נפילה.
- ללא retry אוטומטי לפעולה לא אידמפוטנטית כמו פתיחת ממסר.
- מגבלת מקביליות לכל מכשיר.
- סינון סיסמאות, PIN, מספרי כרטיסים וטוקני QR מהלוגים.
- רישום request ID פנימי לצורך התאמת פעולה לתוצאה.

נתיבי API ידועים כוללים מידע מערכת, מצב, ממסרים, קלטים, שיחה, משתמשים, לוחות זמנים ויומנים. הקטלוג אינו חוזה אחיד לכל הדגמים, ולכן כל הנתיבים יוגדרו בתוך שכבת Akuvox ולא ייחשפו ישירות ל‑UI.

## 10. Action URL ואירועים נכנסים

Akuvox יכולה לדווח לשרת מקומי על שיחה, ניתוק, ממסר, קלט, כרטיס, PIN, פנים ו‑QR. Wiskey תחשוף endpoint מקומי ייעודי לכל תחנה או קבוצה:

```text
POST /api/akuvox/events/{station_id}/{secret}
```

עקרונות קליטה:

- סוד אקראי ארוך בכתובת, ואימות נוסף בכותרת כאשר הקושחה מאפשרת זאת.
- הגבלת כתובות מקור ל‑IP של התחנה.
- הגבלת קצב וגודל בקשה.
- נרמול האירוע למודל אירועים אחיד.
- שמירת זמן מכשיר, זמן שרת וסטיית שעון.
- deduplication לפי מזהה, סוג, תחנה וחלון זמן.
- החזרת תשובה מהירה והמשך עיבוד בתור פנימי.
- polling תקופתי של יומנים כדי להשלים אירועים שאבדו.
- אין לפתוח את endpoint האירועים לאינטרנט.

## 11. QR מקומי

### 11.1 שני מסלולי מימוש

**QR שמנוהל במכשיר:** Wiskey יוצרת או מעדכנת הרשאה דרך ה‑API, והתחנה מאמתת את הקוד מקומית. מסלול זה יופעל רק כאשר הדגם וה‑API תומכים בו באופן מוכח.

**אימות מרוחק מקומי:** התחנה קוראת QR ושולחת את הערך ל‑Wiskey ברשת המקומית. Wiskey מחזירה תשובת הצלחה או כישלון בפורמט שהוגדר במכשיר. התחנה מפעילה את הממסר לאחר תשובה חיובית.

המסלול השני מתאים ל‑Akuvox שתומך ב‑Remote Third‑Party Access Authentication. הוא אינו שירות ענן: השרת המאמת הוא Wiskey ברשת המקומית.

### 11.2 מודל הרשאת QR

```text
QrCredential
- id
- token_hash
- subject_type: visitor | user | delivery | service
- subject_id / display_name
- station_ids
- relay_ids
- valid_from
- valid_until
- max_uses
- used_count
- state: active | expired | revoked | exhausted
- schedule_id (optional)
- created_by
- created_at
- last_used_at
```

ה‑QR יכיל טוקן אקראי של 256 ביט לפחות או payload חתום. בסיס הנתונים ישמור hash של טוקן אטום ולא את הטוקן הגולמי. אין להכניס ל‑QR שם, טלפון, מספר דירה או מידע אישי אחר.

### 11.3 כללי אימות

1. זיהוי התחנה והדלת שמהן התקבלה הבקשה.
2. אימות מקור הבקשה והסוד של התחנה.
3. חישוב hash והשוואה בזמן קבוע.
4. בדיקת תאריך התחלה, תוקף, ביטול, דלתות מותרות ולוח זמנים.
5. נעילה אטומית של מונה השימושים כדי למנוע שימוש כפול מקבילי.
6. רישום אירוע מסונן ללא הטוקן.
7. החזרת התשובה המדויקת שהמכשיר מצפה לה.

יש להוסיף חסימת replay, idempotency לחלון קצר והגבלת ניסיונות. ביטול קוד צריך להיכנס לתוקף מיד במסלול אימות מרוחק.

### 11.4 התנהגות בזמן תקלה

- במסלול אימות מרוחק, ברירת המחדל היא fail closed כאשר Wiskey אינה זמינה.
- כאשר נדרשת שרידות עצמאית, משתמשים ב‑QR שמוטען לציוד או בבקר מקומי עם cache.
- ה‑UI יציג למנהל במפורש אם הרשאה תלויה בזמינות Wiskey.

## 12. משתמשים וסנכרון הרשאות

מודל המשתמש המרכזי של Wiskey נשאר מקור האמת. לכל ספק תישמר התאמה נפרדת:

```text
ProviderUserBinding
- provider
- station_id
- wiskey_user_id
- provider_user_id
- provider_revision / fingerprint
- last_written_at
- last_read_at
- sync_state
- last_error_code
```

כללי סנכרון:

- כתיבה תמיד מסתיימת ב‑read-back ובהשוואת שדות.
- הבדלים מוכרים בנרמול, למשל אפסים מובילים או ייצוג כרטיס, יתועדו בפרופיל הדגם.
- מחיקה תמשיך להשתמש ב‑tombstone עד לאימות שהמשתמש נעלם מכל היעדים.
- conflict לא יידרס אוטומטית אם גם Wiskey וגם התחנה השתנו מאז הסנכרון האחרון.
- import/export המוני יתבצע כתהליך רקע עם התקדמות, ביטול ודוח שגיאות ברמת שורה.
- נתוני פנים יישמרו ויועברו רק לאחר הוספת מדיניות פרטיות ואחסון מתאימה.

## 13. ממסרים, דלתות וקלטים

המודל הקיים צריך לעבור ממבנה של ממסר אחד או שניים לרשימה כללית:

```text
Station
  -> Doors[]
       -> unlock_output: RelayRef
       -> position_input: InputRef | null
       -> exit_button_input: InputRef | null
       -> tamper_input: InputRef | null
```

מצב ממסר אינו בהכרח מצב הדלת. דלת תסומן פתוחה או סגורה רק כאשר יש קלט פיזי מתאים. אם קיים רק ממסר, ה‑UI יציג שהופעלה פקודת פתיחה ולא שהדלת נפתחה בפועל.

## 14. וידאו, שמע ושיחות

### 14.1 וידאו

- RTSP ישמש מקור הווידאו הראשי כאשר קיים.
- ONVIF ישמש לגילוי פרופילים ולשילוב תקני.
- Wiskey תמשיך לתווך stream ל‑Home Assistant כדי לא לחשוף credentials בדפדפן.
- פרופיל הדגם ישמור main/sub stream, codec ורזולוציה.

### 14.2 שמע נכנס

יש לבדוק אם האודיו זמין ב‑RTSP, מהו ה‑codec ומהי התאמתו לנגן של Home Assistant. אם נדרשת המרה, היא תתבצע מקומית.

### 14.3 דיבור דו־כיווני ו‑TTS

מימוש Hikvision הקיים מבוסס ISAPI ו‑G.711 μ‑law ולכן אינו ניתן לשימוש ישיר ב‑Akuvox. הנתיב התקני ל‑Akuvox הוא SIP/RTP מקומי:

- Wiskey תתחבר ל‑PBX מקומי קיים או לשירות מדיה מקומי מבודד.
- התחנה תירשם לחשבון SIP מקומי.
- רכיב המדיה יטפל ב‑RTP, codec, jitter, echo ו‑DTMF.
- TTS יהפוך לקובץ שמע מקומי וישודר בשיחה שנענתה אוטומטית, או ב‑multicast אם הדגם תומך בכך.

אין לסמן `audio.talk` או `audio.tts` כנתמך לפני בדיקה פיזית של כיוון שמע, latency, codec ו‑auto-answer בדגם ובקושחה המדויקים.

## 15. שינויים בבסיס הנתונים

תוספות מוצעות:

- `provider` לכל תחנה.
- `provider_device_id`, דגם, MAC וקושחה.
- `capability_snapshot` עם גרסה וזמן גילוי.
- `provider_config` מוצפן עבור פרטי חיבור לא סודיים וסודות ב‑secret store.
- טבלאות כלליות ל‑doors, relays ו‑inputs.
- `ProviderUserBinding` ו‑`ProviderScheduleBinding`.
- `QrCredential` ויומן שימוש.
- מיפוי סוג אירוע מקורי לסוג אירוע אחיד.

מיגרציה ראשונה:

1. גיבוי סכימה וגרסת נתונים.
2. הוספת השדות החדשים עם ערכי ברירת מחדל.
3. סימון כל התחנות הקיימות כ‑Hikvision.
4. יצירת relay records מהמיפוי הקיים.
5. בדיקת ספירות ו‑foreign keys.
6. מעבר לגרסה החדשה רק לאחר validation מלא.

## 16. ממשק משתמש

### 16.1 אשף הוספת תחנה

- בחירת יצרן.
- כתובת מקומית ופרטי אימות.
- בדיקת חיבור וגילוי דגם.
- מסך יכולות עם הסבר לכל יכולת חסרה.
- מיפוי ממסרים לדלתות וקלטים לחיישנים.
- בדיקת פתיחה מבוקרת.
- הגדרת Action URL אוטומטית כאשר קיימת כתיבה בטוחה, או הוראות מדויקות להגדרה ידנית.
- הגדרת RTSP/ONVIF ו‑SIP לפי הצורך.

### 16.2 מסכי ניהול

- פילטר לפי יצרן, דגם, קושחה וסטטוס הסמכה.
- תגי יכולת במקום הנחות לפי שם המוצר.
- יצירת QR עם תאריך, שעות, דלתות ומספר שימושים.
- ביטול QR מיידי והצגת היסטוריית שימוש.
- אזהרה כאשר תכונה תלויה בשרת, ב‑PBX או בחיישן חיצוני.
- הצגת תוצאות read-back לאחר שינוי הרשאות.

## 17. אבטחה

דרישות חובה:

- חשבון שירות ייעודי לכל תחנה וסיסמה ייחודית.
- Digest או Basic מעל HTTPS; אין להשתמש במצב אימות `None` בסביבה פעילה.
- VLAN ייעודי לציוד, ACL שמאפשר גישה רק בין Wiskey, PBX ותחנות.
- אין port forwarding ואין callback ציבורי.
- שמירת סודות ב‑secret store והסתרתם מ‑backup לא מוצפן ומדיאגנוסטיקה.
- הגנה מ‑CSRF והרשאת מנהל לכל פעולת פתיחה, כתיבה או יצירת QR.
- לוגים אינם מכילים סיסמה, PIN, כרטיס מלא, תמונת פנים או טוקן QR.
- audit בלתי ניתן לעריכה לפעולות פתיחה ושינוי הרשאות.
- rate limit לפתיחת דלת, callbacks, QR וניסיונות התחברות.
- בדיקת clock drift כדי למנוע קבלת קוד שפג תוקפו.
- עדכון קושחה מחוץ ל‑Wiskey בשלב הראשון; Wiskey רק תתריע על שינוי גרסה.

## 19. שלבי מימוש

### שלב A — הכנת ארכיטקטורה רב־יצרנית

תוצרים:

- חוזה `IntercomProvider`.

- מיגרציית בסיס נתונים ותאימות שירותים וישויות.

קריטריון יציאה: כל בדיקות Hikvision עוברות והתקנה קיימת משודרגת ללא שינוי מזהי ישויות או הרשאות.

### שלב B — לקוח Akuvox וגילוי לקריאה בלבד

תוצרים:

- HTTP client עם Basic/Digest/HTTPS.
- קריאת system info, status, relays, inputs וגרסה.
- פרופילי דגם ראשונים ו‑fixtures.
- config flow ודיאגנוסטיקה.

קריטריון יציאה: ניתן להוסיף תחנה, לזהות אותה ולהציג יכולות בלי לבצע כתיבה.

### שלב C — דלתות, אירועים ווידאו

תוצרים:

- הפעלת ממסר עם read-back או אירוע מאמת.
- קלטי דלת וחיישנים.
- RTSP/ONVIF ותמונה.
- endpoint ל‑Action URL, נרמול אירועים ו‑deduplication.

קריטריון יציאה: פתיחה מבוקרת, וידאו ואירועי דלת עוברים בדיקת חומרה רציפה.

### שלב D — משתמשים, כרטיסים ו‑PIN

תוצרים:

- CRUD משתמשים.

- שיוך ממסר ולוח זמנים.
- read-back, conflicts, tombstones וייבוא קיים.
- רישום כרטיס מהאירוע הבא.

קריטריון יציאה: סנכרון דו־כיווני ובדיקת הרשאה אמיתית על כל דגם פיילוט.

### שלב E — יומנים ודוחות

תוצרים:

- door logs ו‑call logs.
- השלמת אירועים שאבדו באמצעות polling.
- שילוב ביומן, בדוחות וב‑audit הקיימים.

קריטריון יציאה: אין כפילויות בין push ו‑poll, ונפילת Wiskey קצרה אינה מאבדת אירועים הנשמרים בציוד.

### שלב F — QR מקומי

תוצרים:

- יצירה, הצגה, ביטול ותפוגה של QR.
- הגבלת דלת, שעות ומספר שימושים.
- Remote Third‑Party Access Authentication בדגמים תומכים.

קריטריון יציאה: קוד חד־פעמי לא ניתן לשימוש פעמיים, ביטול נכנס לתוקף מיד, והמערכת נכשלת במצב סגור בעת ניתוק.

### שלב G — SIP, דיבור ו‑TTS

תוצרים:

- חיבור ל‑PBX או רכיב SIP מקומי.
- מצב שיחה אמין, חיוג וניתוק.
- שמע דו־כיווני.
- TTS מקומי.

קריטריון יציאה: איכות שמע ו‑latency מקובלים ברשת היעד; אין תלות באינטרנט; התאוששות לאחר ניתוק שיחה נבדקה.

### שלב H — יכולות מתקדמות

פנים, אימות דו־שלבי, לוחיות, מעלית, lockdown ו‑hold-open יתווספו בנפרד ורק לאחר בדיקת API, אבטחה וחומרה.

## 20. אסטרטגיית בדיקות

### 20.1 בדיקות אוטומטיות

- contract tests משותפים לכל ספק.
- unit tests למיפוי API, נרמול שדות ושגיאות.

- בדיקות QR: תפוגה, ביטול, שימוש יחיד, מקביליות, replay ושעון סוטה.
- בדיקות callbacks: payload חסר, מקור שגוי, כפילות, סדר אירועים הפוך ועומס.
- בדיקות sync: partial failure, conflict, read-back שונה ו‑tombstone.
- בדיקות UI לפי capability חסרה.

### 20.2 בדיקות חומרה

לכל שילוב דגם וקושחה:

- restart של תחנה ושל Wiskey.
- ניתוק רשת והתחברות מחדש.
- פתיחת כל ממסר ובדיקת החיישן המתאים.
- כרטיס תקין ושגוי, PIN תקין ושגוי ו‑QR תקין ושגוי.

- RTSP למשך זמן ממושך.
- שינוי משתמש בזמן שהמכשיר עמוס.
- שינוי שעון וקושחה.
- אימות שכל פעולה מופיעה פעם אחת ביומן.

### 20.3 בדיקות עומס

- סנכרון אלפי משתמשים בקבוצת תחנות.

- תור פעולות לאחר חזרת תחנה offline.

פתיחת דלת לא תישלח מחדש אוטומטית לאחר חזרת מכשיר לרשת.

## 21. הסמכת דגמים

כל שילוב דגם וקושחה יקבל אחד מהמצבים:

מטריצת ההסמכה תכלול:

- דגם וגרסת חומרה.
- גרסת קושחה.
- מספר ממסרים וקלטים.
- משתמשים, כרטיסים, PIN ו‑schedule.
- QR מובנה ו‑remote validation.
- RTSP, ONVIF, SIP, talk ו‑TTS.
- מגבלות ידועות וקישור ל‑fixture.

אין לפרסם "תמיכה מלאה ב‑Akuvox". יש לפרסם את הדגמים והגרסאות שנבדקו ואת היכולות של כל אחד.

## 22. ציוד פיילוט מומלץ

כדי להשלים את הפיתוח נדרשים לפחות:

- רשת מבודדת עם DNS ו‑NTP מקומיים.
- חשבון מנהל וחשבון שירות נפרד.

בחירת הדגמים הסופית תיעשה סמוך לפיתוח לפי מלאי בישראל, גרסת קושחה זמינה ותיעוד API שהיצרן מאשר לאותו דגם.

## 23. Definition of Done לתמיכת Akuvox ראשונה

גרסה ראשונה תיחשב מוכנה כאשר:

- גילוי יכולות מונע הצגת פעולות לא נתמכות.
- פתיחת ממסר, מצב דלת, RTSP ואירועים פועלים מקומית.
- משתמשים, כרטיסים, PIN ולוחות זמנים עוברים כתיבה ו‑read-back.
- QR מקומי כולל תפוגה, ביטול, הגבלת שימוש ו‑audit.
- אין סוד או credential בדיאגנוסטיקה ובלוגים.
- פעולות רגישות דורשות הרשאת מנהל ונרשמות ב‑audit.
- ניתוק אינטרנט אינו משפיע על יכולות שהוגדרו כמקומיות.
- מגבלות SIP, שמע ו‑TTS מוצגות לפי capability שנבדקה בפועל.
- התיעוד כולל טבלת דגמים וקושחות מוסמכות, הוראות רשת ושחזור מתקלה.

## 24. סיכונים ידועים

- API ושדות שונים בין משפחות וגרסאות קושחה.
- Action URL אינו זהה בכל דגם ואירועים מסוימים אינם קיימים בכולם.
